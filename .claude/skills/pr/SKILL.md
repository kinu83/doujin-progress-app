# pr

## 手順

1. 現在のブランチ名を確認する。ブランチ名は `feature/機能名`（例：`feature/personal-tasks`）。main 上にいる場合は作業を止めてユーザーに確認する。
2. `git fetch` のあと、`git log origin/main..HEAD` と `git diff origin/main...HEAD` で PR に含まれる変更を確認する。未コミットの変更があれば、先に commit を使うか確認する。
3. 対応する Issue 番号を確認する（ブランチを作ったときの Issue、コミット、会話から分かる範囲で。分からなければユーザーに聞く）。
4. 下の形式でタイトルと本文を作る。
5. push するブランチ名、PR のタイトル・本文をユーザーに見せ、承認を得る。
6. 承認されたら `git push -u origin <ブランチ名>` → `gh pr create --base main --title ... --body-file ...` を実行する。本文は一時ファイルに書いて `--body-file` で渡す。
7. 作成した PR の URL を報告する。

## タイトル

- コミットメッセージと同じ `種別:日本語の要約` の形式（コロンのあとにスペースを入れない）。
- コミットが1つならそのメッセージ、複数なら PR 全体を表す要約にする。

## 本文

```markdown
## 何を変えたか
- （変更点を箇条書き）

## なぜ変えたか
- （目的・背景）

Closes #<Issue番号>

## 動作確認
- （確認した手順。未確認のものは「未確認」と明記する）
```

- 対応する Issue がない場合は `Closes #...` の行を書かない。

## 注意点

- push・PR 作成の実行前に、必ず内容をユーザーに見せて承認を得る。承認は1回ごとに取り、「前にOKをもらったから」と次の実行まで進めない。
- 差分に含まれていない変更は書かない。
- 実際に行っていない動作確認は書かない。この会話で実行して成功したもの（`npm run typecheck`、`npm run build`、画面確認など）だけを書き、それ以外は「未確認」と書く。
- 向き先は必ず `main`。
- `git push --force` は使わない。
